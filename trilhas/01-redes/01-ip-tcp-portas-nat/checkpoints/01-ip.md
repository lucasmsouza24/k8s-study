### Q1 · O que é

O que um endereço IP identifica? Para que ele é usado quando um pacote sai do seu notebook e vai até um servidor na internet?

> Um endereço IP identifica dispositivos na rede, sejam redes públicas ou privadas. O protocolo IP determina um cabeçalho onde é especificado não só a origem/destino da comunicação, mas também informações como "qual o tamanho do conteúdo do pacote (payload)", "quantos saltos o pacote pode fazer na rede (TTL)" e várias outras informações sobre a comunicação. Basicamente o protocolo IP determina uma série de regras para que a comunicação entre 2 dispositivos na rede aconteça. É como se o IP fosse a linguagem que os dois dispositivos tem que saber falar, seguinto as regras gramaticais metafóricas

**Correção — 2/2.** Ótima resposta: identificação, cabeçalho com origem e destino, TTL e tamanho. Um ajuste de precisão: o IP identifica uma **interface de rede**, não o dispositivo. Um mesmo computador pode ter vários IPs, um por interface, como a sua Q10 mostra. Cuidado também para a analogia da "linguagem" não misturar duas coisas: o **endereço** IP (o número) e o **protocolo** IP (as regras e o cabeçalho).

### Q2 · Formato do IPv4

Quantos bits tem um endereço IPv4 e como ele é escrito? Por que cada um dos números vai de 0 a 255? Aproximadamente quantos endereços IPv4 existem no total?

> Um endereço IPv4 possui um conjunto de 4 bytes (32 bits). Cada byte é separado por pontos, seguindo o seguinte formato:
>
> 0.0.0.0 -> 255.255.255.255
>
> 8 bits conseguem representar 256 valores possíveis (0 -> 255) e como o IPv4 tem 4 partes de um byte: 4 bytes -> 32 bits -> 2³² valores únicos possíveis

**Correção — 2/2.** Completo. Para ter o número na cabeça: 2³² ≈ **4,3 bilhões**. Menos do que a população do planeta, e é por isso que existem o IPv6 e o NAT.

### Q3 · Válido ou não

Para cada item, diga se é um endereço IPv4 válido e por quê:

a) `10.0.0.1`
b) `192.168.1.256`
c) `172.16.300.4`
d) `8.8.8.8`
e) `1.2.3`
f) `0.0.0.0`

> a) válido, valores estão dentro da faixa esperada  
> b) inválido, por conta do 256  
> c) inválido por conta do 300  
> d) teóricamente válido, mas tenho dúvidas, pois  está abaixo da classe A (10.0.0.0 -> 10.255.255.255). Apesar de que eu reconheço esse endereço 8.8.8.8 como sendo o endereço DNS da Google  
> e) inválido, possui apenas 3 termos  
> f) referente à faixa de valores está válido, porém esse valor é reservado, assim como o 127.0.0.1, e não posse ser atribuído para dispositivos

**Correção — 2/2.** Os seis veredictos estão certos. Dois ajustes:
- **d)** `8.8.8.8` é um IP **público** válido (o DNS do Google, como você lembrou). A sua dúvida mistura dois conceitos: a "classe A" antiga eram os endereços com o primeiro número de 0 a 127; `10.0.0.0–10.255.255.255` é a **faixa privada** que fica dentro dela. Além disso, as classes A/B/C estão obsoletas desde os anos 90, substituídas pelo CIDR, que é justamente o próximo assunto.
- **f)** Certo: é reservado e não é atribuído a um dispositivo. O significado depende do contexto. Quando um **servidor escuta** em `0.0.0.0`, quer dizer "em todos os meus endereços". Isso é diferente do `127.0.0.1`, e vai aparecer no Lab 2.

### Q4 · IPv6

Por que o IPv6 foi criado? Quantos bits ele tem e como é escrito? O que significa `::1`, e por que dá para abreviar um endereço IPv6 usando `::`?

> O IPv4 teoricamente suporta algo próximo de (2³²) - 2 dispositivos, isso pode parecer bastante mas em algum momento vamos esgotar os endereços possívies. Pensando nisso o IPv6 foi criado para suprir essa necessidade de possuir mais endereços possíveis. Não estudei sobre os outros detalhes ainda.

**Correção — 1/2.** O motivo está certo: esgotamento de endereços. O que falta:
- **128 bits**, escritos como 8 grupos de 4 dígitos hexadecimais separados por `:`. Ex.: `2804:07f0:75c0:5666:fe8c:2b7c:06f3:27c3`.
- Abreviações: zeros à esquerda de cada grupo podem ser omitidos (`07f0` → `7f0`), e **uma única** sequência de grupos só de zeros pode virar `::`. Só uma vez, senão não daria para saber quantos zeros cada `::` representa.
- `::1` = `0000:0000:0000:0000:0000:0000:0000:0001`, o **loopback do IPv6**, o equivalente ao `127.0.0.1`.

Sobre o "(2³²) − 2": a ideia de descontar endereços reservados está certa, mas são muitos mais do que 2. Faixas inteiras são reservadas: privadas, loopback, multicast etc.

### Q5 · Loopback

O que é `127.0.0.1` (ou `localhost`)? Um pacote enviado para esse endereço passa pela placa de rede ou pelo Wi-Fi? Quando você roda um servidor no notebook e o acessa por `localhost`, por onde a comunicação passa?

> 127.0.0.1 é um endereço reservado, assim como 0.0.0.0. Eu entendo o localmente como uma auto referência do dispositivo. Preciso estudar mais pra definir com mais precisão.

**Correção — 1/2.** "Autorreferência" está certo. A parte que faltou é a mais útil:
- O loopback é uma **interface virtual** do kernel (`lo`, na sua Q10). Pacotes enviados para ela **nunca saem da máquina**: não passam pela placa de rede nem pelo Wi-Fi. Funciona até com o cabo desconectado.
- Toda a faixa `127.0.0.0/8` é loopback, não só o `.1`.
- Consequência prática: um servidor que escuta só em `127.0.0.1` só é acessível **da própria máquina**. Dentro de um container, "a própria máquina" é o próprio container. Esse é o motivo de um bug clássico que você vai provocar no Lab 4.
- `0.0.0.0` também é reservado, mas tem outro significado (ver Q3-f).

### Q6 · Público × privado

Sem se preocupar com as faixas exatas: qual a diferença entre um IP público e um IP privado? Por que dois notebooks, em casas diferentes, podem ter exatamente o mesmo IP `192.168.0.10` sem conflito?

> Um endereço de IP público está visível para toda a internet pois faz parte da rede pública, e precisa ter um valor único dentro desse ambiente público. Um endereço privado não trata de dispositivos da rede pública, e sim de uma rede privada. Como é uma outra rede, pode ter um endereço "repetido" que já é encontrado na rede pública. Mas é importante afirmar que dentro da rede privada o endereço precisa ser único em relação aos demais dispositivos da rede privada. Também é importante deixar claro que de forma geral, cada rede doméstica possui apenas 1 dispositivo com um endereço IP público (geralmente o roteador), e uma rede interna (privada) utiliza o dispositivo roteador como entrada/saída das requisições. por isso cada dispositivo dentro da rede privada recebe um ip privado (celulares, computadores, TVs, etc)

**Correção — 2/2.** Excelente, incluindo o detalhe de que o endereço privado precisa ser único **dentro** da rede privada. O que você descreveu no final, o roteador como única entrada e saída com o IP público, tem nome: **NAT**. Ele traduz os IPs privados para o público na saída. Os IPs privados podem se repetir porque os roteadores da internet **não encaminham** pacotes com esses endereços. Curiosidade: muitos provedores hoje nem dão um IP público ao seu roteador e fazem um segundo NAT do lado deles (CGNAT), por falta de IPv4.

### Q7 · IP dinâmico × fixo

Como o seu notebook recebe um IP quando se conecta a um Wi-Fi? O que acontece com esse IP quando ele se conecta a outra rede? Por que um servidor normalmente precisa de um IP fixo?

> Depende da configuração de rede. O mais cômodo é ativar o protocolo DHCP, que atribui ao dispositivo automaticamente um endereço de IP disponível dentro da rede em questão (dinâmico). Alternativamente, o IP do dispositivo pode ser atribuido de forma manual (fixo) é necessário ter conhecimento sobre qual a faixa de endereços válidas e disponíveis da rede em questão. O DHCP recebe o nome "Dinâmico" por que seu endereço pode ser alterado ao alternar entre redes, o que não é algo esperado de um Servidor. Em um Servidor o interessante é que o valor seja sempre o mesmo, para que os clients sempre saibam chegar até lá (via DNS).

**Correção — 2/2.** Certo: DHCP × manual, e o servidor precisa de IP fixo porque o DNS aponta para ele. Dois ajustes de precisão:
- Quem entrega o IP é um **servidor DHCP**, que em casa geralmente é o próprio roteador. O IP vem com um prazo (*lease*) e pode mudar mesmo **sem** trocar de rede, quando esse prazo expira.
- O "D" do DHCP é de *Dynamic Host Configuration*: a configuração é feita automaticamente. Trocar de rede muda o IP em qualquer caso, porque um IP só faz sentido **dentro** da rede onde ele está. Um IP fixo configurado na mão também deixaria de funcionar em outra rede.
- Além do IP, o DHCP entrega a máscara, o *default gateway* (Q8) e o servidor DNS.

### Q8 · Roteamento

O seu notebook envia um pacote para `142.250.0.1`, um servidor fora da sua rede. Ele não conhece o caminho até lá. Para quem ele entrega o pacote? Com base em que informação cada equipamento no caminho decide para onde encaminhar?

> Dentro da rede interna, esse endereço não será encontrado, portanto será passado para o roteador, que vai se comunicar com outros dispositivos da rede pública (até onde sei, baseados no IP e suas regras matemáticas) até encontrar o endereço final. Talvez eu precise entender algo a mais sobre o processo.

**Correção — 1/2.** Certo que o pacote vai para o roteador; esse papel tem nome: **default gateway**. O que faltou é o mecanismo, e a intuição de "até encontrar" engana: nenhum roteador procura o destino nem conhece o caminho inteiro.
- Cada roteador olha **só o IP de destino** do pacote, consulta a sua **tabela de rotas** e o entrega ao **próximo salto** (*next hop*). O caminho é decidido um salto por vez.
- A cada salto, o **TTL** (que você citou na Q1) diminui 1. Se chegar a 0, o pacote é descartado, o que impede loops infinitos.
- Você pode ver isso no Lab 1 com `ip route` (sua tabela de rotas) e, se quiser, com `tracepath 142.250.0.1` (os saltos até o destino).

### Q9 · Melhor esforço

O protocolo IP garante que um pacote chega ao destino, chega uma única vez e na ordem certa? Se não garante, quem cuida disso?

> Não garante. O protocolo IP apenas determina o formato da comunicação, como os endereços são definidos, quais e como as informações são descritas no cabeçalho, etc. Quem cuida de "como" a comunicação acontece são outros protocolos como TCP, UDP, etc

**Correção — 1/2.** O "não garante" está certo, mas há dois ajustes:
- O IP não só define o formato: ele **entrega** o pacote, salto a salto (Q8). Só que sem garantias. Isso se chama *best effort* (melhor esforço).
- Quem garante entrega, ordem e ausência de duplicatas é o **TCP** (com confirmações, retransmissões e números de sequência). O **UDP também não garante nada**: ele só adiciona portas ao IP. Usa-se UDP quando a velocidade importa mais do que a garantia, como no DNS e em chamadas de vídeo. Isso é o item 3 do roteiro.

A sua máquina, lida por completo:

| Interface | O que é | Endereços | Público ou privado |
|---|---|---|---|

| `enp3s0` | sua placa de rede cabeada (*en* = ethernet) | `192.168.15.6` | **privado** (faixa `192.168.x.x`), recebido do roteador via DHCP |
| | | `2804:7f0:...` | **público**! No IPv6 geralmente não há NAT: cada dispositivo recebe um endereço global |
| | | `fe80::...` | *link-local*: gerado automaticamente, só vale no próprio segmento de rede |
| `docker0` | bridge padrão do Docker | `172.17.0.1` | privado (faixa `172.16–172.31`) |
| `br-83bdbb5ac474` | bridge de uma rede Docker criada pelo **minikube** | `192.168.49.1` | privado. O seu minikube é o `192.168.49.2`, o endereço que aparecia no kubeconfig |

O `/8`, `/24` e `/64` depois de cada endereço são CIDR: é exatamente o que você vai estudar agora.
